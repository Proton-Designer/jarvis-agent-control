Design study · terminal interface

Three consoles for Jarvis

Jarvis runs as a daemon, an orchestrator session, and a fleet of Claude Code panes. Right now you drive all of it from memorised commands. These are three ways the control surface could look — the same functionality, at three different densities.

What the interface has to do

Four things, and only four. Show and stop the microphone — unambiguous status, plus a control that only ever stops it (space is stop-only, never a toggle — accidentally stopping is recoverable, accidentally starting isn't; starting is a separate, deliberate action). Set up or reconnect the orchestrator — three states, and the interface must show which one is true rather than which one it last attempted. Show the fleet — every session Jarvis can reach, and what it is doing. Stream what is happening — wake scores, state transitions, routing decisions, as they occur.

The last one is the reason a terminal wins. A graphical app would compress all of that into a status light. Here it can be the main event.

What it's good at

  • Nothing is hidden behind a keystroke — memory pressure, model warmth and tool health are all just visible.
  • The stream sits beside the controls, so cause and effect are read together.
  • Scales to a fleet: the sessions panel is the natural home for ten projects.

What it costs

  • Wants a full window. Cramped below roughly 100 columns.
  • Most of the surface is idle most of the time — you are usually only doing one thing.
  • The most safety-critical control, the microphone, gets the same visual weight as memory statistics.

Idle, the same screen collapses: the state block reads LISTENING, the pipeline greys out, and the transcript panel is replaced by the last routing summary.

PIPELINE and HEARD SO FAR, above, are deliberately deferred — not built, and not a gap between this mockup and the real console (see docs/SPEC-TUI.md §3, "Signal's PIPELINE / HEARD SO FAR panels"). The live meter is the load-bearing element and already exists; these two answer questions nobody has asked for yet, so they wait until Ayman actually wants more than the meter gives him.

What it's good at

  • Answers the question you actually have mid-dictation: is it still hearing me?
  • The live meter is real feedback — it moves when you speak, so a dead microphone is obvious instantly.
  • Teaches the system's shape. After a week you would know exactly where a failure happened.

What it costs

  • Optimised for the sixty seconds you are talking, not the hours you are not.
  • Fleet management gets demoted to a second view.
  • The most animated design, and animation in a terminal is where taste goes to die if overdone.

What it's good at

  • Lives in a narrow pane forever without stealing space from your actual work.
  • Always visible, which makes it a genuine microphone indicator rather than a screen you check.
  • Smallest thing to build, and the least to maintain as the system changes.

What it costs

  • Setup and reconnect need a modal or an expanded view — there is no room inline.
  • Diagnostics get compressed to the point of being hints rather than answers.
  • Undersells the system. It looks like a status bar, not the thing running your fleet.

Adopt what's running

  • Live sessions grouped by working directory — the directory is the team.
  • Each agent shown with its model and its own self-written summary, so you choose informedly.
  • Nothing is inferred about roles. The system never learns what a “lead” is.

Start fresh

  • Pick a directory, choose how many agents and which model each runs.
  • Sessions are created, launched, and the trust prompt pre-answered — no terminal work.
  • Same two questions at the end: who receives, what do you call it.

Where I'd land

Rail as the default, Console one keystroke away, and Signal's live meter borrowed into both.

The three are not really competing — they are the same application at three window sizes, which is exactly what a modern TUI framework handles natively. Build the state layer once and let the layout respond to the space it is given: in a narrow pane you get Rail, full-screen you get Console, and during an active dictation the state block and meter take over regardless of size.

The one piece I would take from Signal no matter what is the live audio meter. Every other element reports what the system believes; the meter reports what the microphone is actually receiving. When something goes wrong at three in the morning, that is the difference between debugging and guessing.

Framework research is running in parallel — Textual, Ratatui, Bubble Tea and the current field — and will decide how much of this is free versus hand-built.
